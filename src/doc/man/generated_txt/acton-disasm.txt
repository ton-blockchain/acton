ACTON-DISASM(1)

NAME
       acton-disasm — Disassemble TVM bytecode into human-readable TASM

SYNOPSIS
       acton disasm [options] [boc-file]

DESCRIPTION
       Disassemble compiled TVM bytecode from a file, a literal BoC string, or
       a live contract address.

       This command is useful for debugging compiler output, inspecting
       deployed code, following library references, and correlating bytecode
       with Tolk source via source maps.

OPTIONS
   Disassembly Options
       boc-file
           Binary, hex, or base64 BoC file to disassemble.

           Use --string to pass the code directly instead of reading a file.

           Available since trunk.

           A .tolk file is compiled as an entrypoint before disassembly.
           Imports use the project mappings from Acton.toml. Files without an
           entrypoint are also accepted. Use --function to select individual
           functions from these sources.

       --function name
           Available since trunk.

           Disassemble only the named function from a .tolk input. Repeat this
           option to select multiple functions, including functions declared in
           imported files. Functions are printed in the requested order;
           repeated names are printed once. All names in one invocation share
           the same compilation passes.

           Selected functions keep separate bytecode bodies, even if normally
           inlined or unused. This inspection build leaves source files and
           build artifacts unchanged. Its bytecode can differ from a normal
           optimized build.

           Supports non-generic functions with block bodies and no receiver or
           mutate parameters, get-methods, and external entrypoints.
           Get-methods and functions with an explicit @method_id keep their
           IDs. Generic functions, receiver methods, asm functions, and
           onBouncedMessage cannot be selected.

           Requires a .tolk file. Cannot be used with --source-map, --string,
           --address, or --follow-libraries.

       -s, --string string
           BoC value in hex or base64 format.

       -o, --output path
           Write plain disassembly text to a file.

           Without --json, this replaces standard output. With --json, Acton
           still prints the JSON envelope to stdout and writes only the
           assembly field to the file.

           If the parent directory does not exist, Acton creates it
           automatically. Existing files are overwritten.

       --show-hashes
           Show cell hashes alongside code blocks.

       --show-offsets
           Show instruction bit offsets in the left column.

       --json
           Print machine-readable disassembly JSON to stdout.

           Successful output includes success, the plain disassembly in
           assembly, and blocks derived from --source-map or the compiled Tolk
           source. For BoC input without --source-map, blocks is empty.

       --source-map path
           Use a source map to show original Tolk source locations together
           with disassembly output.

           Available since trunk.

           This option applies to BoC input. Recompiled .tolk input does not
           accept an external source map.

       --address address
           Fetch contract code from the blockchain by address and disassemble
           it.

       --net network
           Network to use for --address and library lookups.

           Supported values: mainnet, testnet, localnet, custom:<name>.

           localnet and custom:<name> resolve through the project network
           configuration in Acton.toml.

           If omitted, Acton tries mainnet first and then falls back to
           testnet.

       --follow-libraries
           If the input disassembles to exactly one top-level exotic
           library-reference cell, fetch and disassemble the actual library
           code instead of showing only the library hash reference.

           This is not a general recursive library-follow mode.

   Display Options
       --color when
           Control when to use colored output.

           Possible values: auto, always, never

   Project Options
       --manifest-path path
           Path to the Acton.toml file to use for this invocation.

           Use this when running the command outside the project directory or
           when the manifest lives at a non-default location.

       --project-root path
           Path to the project root to use for configuration discovery and
           relative defaults.

           This conflicts with --manifest-path.

BLOCKCHAIN LOOKUPS
       When --address is used, Acton fetches code from the selected network.

       o  --net accepts mainnet, testnet, localnet, and custom:<name>

       o  localnet and custom:<name> use URLs from Acton.toml

       o  Without --net, Acton tries mainnet first and then testnet

       o  with --address, --follow-libraries reuses the network that returned
          the contract code

       When --follow-libraries is used with a local file or --string, Acton
       uses the explicit --net if provided; otherwise library fetches default
       to testnet.

TON CENTER API KEYS
       Built-in mainnet/testnet requests read TONCENTER_MAINNET_API_KEY or
       TONCENTER_TESTNET_API_KEY, depending on the selected network.

       For custom:<name>, Acton reads <NORMALIZED_NAME>_API_KEY. Custom network
       names are uppercased and non-alphanumeric characters are replaced with
       _, so custom:mock-remote becomes MOCK_REMOTE_API_KEY.

       Acton loads .env automatically, so the simplest setup during project
       work is usually to keep these keys there and use shell environment
       variables only for one-off overrides or CI.

INPUT PRECEDENCE
       o  BOC_FILE and --string are mutually exclusive

       o  --address is used only when neither a file nor --string is provided

       o  --follow-libraries only replaces the input when the initial
          disassembly is exactly one top-level exotic library-reference cell
          and the lookup succeeds

       o  ordinary code, mixed instruction streams, or nested library
          references are a no-op for --follow-libraries

       o  if library lookup fails, Acton warns and disassembles the original
          code instead; this still exits successfully

SOURCE MAPS
       If you compiled a contract with acton compile --source-map, you can pass
       that source map JSON here to annotate the disassembly with original Tolk
       locations.

       --source-map only affects annotations in the output. It does not change
       which BoC is disassembled.

JSON OUTPUT
       With --json, Acton prints pretty-printed JSON to stdout.

       o  success: true for successful disassembly

       o  assembly: plain disassembly text without inline source-map comments

       o  blocks: source-to-assembly mappings derived from --source-map

       Each item in blocks contains a source location and assembly_ranges.
       assembly_ranges stores inclusive zero-based start_line/end_line pairs
       into the assembly string.

       For BoC input, blocks is empty without --source-map. Tolk source input
       includes mappings from its inspection compilation automatically.

       If --output is also provided, the output file contains the same plain
       assembly text while stdout remains JSON.

       Available since trunk.

       With --function, the response also includes a functions array in the
       requested order. Each item contains name, method_id, assembly, blocks,
       and gas_estimate. The per-function assembly contains only that
       function’s instructions. Its blocks use line offsets into that
       function’s assembly; top-level blocks use offsets into the combined
       assembly, including function headers. Source locations refer to the
       original files, before annotation overrides. Identical bytecode may
       share a cell whose source marks were retained for only one function.
       Functions without matching marks have empty blocks; Acton does not
       attribute another function’s source locations to them.

       gas_estimate contains:

       o  value: sum of the lowest listed opcode costs from the bundled TVM
          specification

       o  has_dynamic_cost: costs depend on runtime data or include a formula

       o  has_control_flow: the body contains control flow or nested
          continuations

       o  unknown_instructions: instructions whose cost could not be included

       The estimate counts each instruction and nested continuation once. It
       does not predict the path taken through branches or the number of loop
       iterations. It excludes callees, implicit returns, dispatcher overhead,
       stack-copy charges, and additional data-dependent fees. It is neither a
       lower nor an upper bound on runtime gas. Use execution profiling when
       inputs and actual gas costs matter.

       For example, fun increment(value: int): int { return value + 1; } has
       this entry:

           {
             "name": "increment",
             "method_id": 262143,
             "assembly": "INC\n",
             "blocks": [
               {
                 "source": {"file": "example.tolk", "line": 1, "column": 41, "end_line": 1, "end_column": 50},
                 "assembly_ranges": [{"start_line": 0, "end_line": 0}]
               }
             ],
             "gas_estimate": {
               "value": 18,
               "has_dynamic_cost": false,
               "has_control_flow": false,
               "unknown_instructions": 0
             }
           }

       Generated method IDs are local to the inspection build. Identify
       functions by name when matching results to an editor document.

EXIT STATUS
       o  0: Disassembly completed successfully, including runs with unresolved
          library references that were left as warnings.

       o  1: BoC input was invalid, a blockchain fetch failed, source-map
          loading failed, or the output file could not be written.

EXAMPLES
       Available since trunk.

       Disassemble selected functions from a Tolk entrypoint:

           acton disasm contracts/jetton-wallet.tolk --function transfer --function get_wallet_data

       1. Disassemble a local BoC file:

              acton disasm contract.boc

       2. Disassemble a literal BoC string:

              acton disasm --string "b5ee9c72010104...0840f01c700f2f4"

       3. Disassemble code from a blockchain address:

              acton disasm --address UQA_ftKIJsHEAE_UgtFOUK15hPzycZooFuUr8duyY9T3kwwM --net testnet

       4. Show hashes, offsets, and source locations:

              acton disasm contract.boc --show-hashes --show-offsets --source-map contract.json

       5. Inspect deployed code together with hashes:

              acton disasm --address UQA_ftKIJsHEAE_UgtFOUK15hPzycZooFuUr8duyY9T3kwwM --show-hashes \
                                                                                      --net testnet

       6. Write disassembly to a nested output path:

              acton disasm contract.boc --output build/disasm/contract.tasm

       7. Resolve a top-level library-reference cell using a configured custom
          network:

              acton disasm library-ref.boc --follow-libraries --net custom:staging

       8. Print machine-readable JSON with source-map ranges:

              acton disasm contract.boc --source-map contract.json --json
